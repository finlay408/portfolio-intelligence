## 1. What this is

A single-user, private portfolio analytics platform. Not a performance tracker — a risk and
attribution system. The owner enters trades once; every position, weight, exposure, return
decomposition and risk metric is derived from that ledger and recomputed automatically.

**Owner profile:** UK-based. Base currency **GBP**. Holds US-listed and LSE-listed equities and
ETFs. Uses regular auto-invest contributions. Wants institutional-grade analytics without paying
for data.

**Non-negotiables:**

1. £0/month recurring data cost.
2. Deployed on Vercel, accessible only to the owner.
3. Trades entered manually or generated by auto-invest rules. No other manual input, ever.
4. No LLM required at runtime. The app must run standalone and indefinitely.
5. Every derived number must be reproducible from the trade ledger + price history.

---

## 2. The single most important architectural rule

**Positions are never stored. They are always derived.**

The `trades` table is append-only and is the sole source of truth. Holdings, cost basis, realised
P&L, unrealised P&L, weights, and every exposure figure are computed on read from the full trade
history plus corporate actions.

This is what makes sells, partial closes, splits and rebalances work without intervention. It is
also what most home-built trackers get wrong: they mutate a `positions` table, drift from reality
within six months, and the owner loses trust in the numbers.

Corollary: any bug in the position engine is fixed once, and every historical figure corrects
itself on the next recompute. Cached snapshots are a performance optimisation only, and must be
fully rebuildable with a single command (`pnpm recompute --from=inception`).

## 3. Currency handling — read this before writing any code

The portfolio is GBP-based and holds USD assets. This creates three traps.

### 3.1 LSE prices are quoted in pence

Yahoo Finance returns LSE-listed instruments in **GBX (pence)**, not GBP. A price of `2450.0` for
a UK stock means £24.50. This is the single most common bug in UK portfolio software.

Handle it in the schema, not in ad-hoc code: every instrument carries a `quote_currency` and a
`quote_multiplier`. For GBX instruments, `quote_currency = 'GBP'` and `quote_multiplier = 0.01`.
Normalise **at the ingestion boundary** so that nothing downstream ever sees pence. Write a unit
test asserting a known LSE close converts correctly.

Some instruments quote in GBX and some in GBP on the *same* exchange (many ETFs quote in GBP or
USD on the LSE). Do not infer from the `.L` suffix — store it per instrument and verify on first
ingest by sanity-checking against a known reference.

### 3.2 Return decomposition

Every non-GBP position's return must be split:

```
total_return_gbp ≈ asset_return_local + fx_return + (asset_return_local × fx_return)
```

Store and display these separately. The cross term is small but include it for exactness rather
than dropping it. Without this split, "alpha vs S&P 500" is contaminated by GBP/USD moves and the
factor regressions are meaningless.

### 3.3 Benchmark comparison

When comparing to the S&P 500, offer both:

- **GBP-translated SPX** — the return the owner would actually have earned. Default view.
- **Local-currency SPX** — the correct comparison for judging security selection.

Label them unambiguously in the UI. Alpha, beta, tracking error and information ratio should be
computed against both and shown side by side.

## 4. Stack

| Layer | Choice | Reason |
|---|---|---|
| Framework | Next.js (App Router), TypeScript, strict mode | Vercel-native |
| Database | Postgres — Neon or Supabase free tier | Relational, free, generous limits |
| ORM | Drizzle | Typed, lightweight, good migrations |
| Analytics compute | TypeScript for simple stats; **Python for regressions, VaR, factor models** | See §4.1 |
| UI | React, Tailwind, shadcn/ui | Fast, consistent |
| Charts | Recharts for standard; D3 for RRG | RRG needs custom trails |
| Scheduler | **GitHub Actions**, not Vercel Cron | See §4.2 |
| Auth | Vercel Deployment Protection (SSO) *or* NextAuth email magic link | Single user |

### 4.1 Two-runtime split

Portfolio maths (position engine, weights, TWR, contribution) lives in TypeScript so the web app
can compute it directly.

Statistical work — OLS factor regressions, Cornish-Fisher VaR, covariance estimation, PCA —
belongs in Python with numpy/pandas/statsmodels. Reimplementing these in TypeScript is a large
source of subtle error for no benefit.

The Python side runs as a scheduled job (§4.2), writes results into `analytics_snapshots`, and the
web app reads them. The web app never calls Python synchronously.

### 4.2 Scheduling — do not use Vercel Cron

Vercel's Hobby tier restricts both the number of cron jobs and their frequency, and its serverless
function timeout is too short for a full nightly analytics rebuild. **Verify the current limits
before relying on them.**

Use **GitHub Actions scheduled workflows** instead. They are free for public and private repos at
this scale, support minute-level granularity, have generous timeouts, and can run Python natively.

Two patterns:

- **Light jobs** (quote refresh) — Action calls a protected Next.js API route with a shared secret.
- **Heavy jobs** (nightly analytics) — Action runs Python directly and writes to Postgres over the
  connection string. Never round-trips through Vercel.

Store `DATABASE_URL`, provider API keys and `CRON_SECRET` in GitHub repository secrets.

## 6. Provider abstraction

Every external data source sits behind one interface. yfinance **will** break — treat that as a
certainty, not a risk. When it does, swapping providers must be a config change.

```ts
interface PriceProvider {
  readonly name: string;
  readonly supports: (inst: Instrument) => boolean;
  readonly delaySeconds: number;

  getQuote(insts: Instrument[]): Promise<Quote[]>;
  getDailyBars(inst: Instrument, from: Date, to: Date): Promise<Bar[]>;
  getCorporateActions?(inst: Instrument, from: Date): Promise<CorporateAction[]>;
}
```

Routing table, in priority order:

| Instrument | Primary | Fallback |
|---|---|---|
| US equity/ETF quote | Alpaca (real-time IEX, WebSocket) | Finnhub → Yahoo |
| US daily bars | Alpaca | Yahoo |
| LSE quote | Yahoo (`.L`, ~15-20 min delayed) | Finnhub |
| LSE daily bars | Yahoo | Alpha Vantage (batch, 25/day) |
| FX | FRED (`DEXUSUK`) daily; exchangerate.host intraday | Yahoo `GBPUSD=X` |
| Corporate actions | Yahoo + Finnhub, cross-checked | manual entry UI |
| Earnings calendar | Finnhub (60 req/min) | Yahoo |
| Macro | FRED | — |
| Factors | Ken French Data Library (CSV, free) | — |
| Options chains + Greeks | Alpaca indicative feed (free, includes delta/gamma/theta/vega/rho, IV, OI) | compute via Black-Scholes |

Rules the resolver must enforce:

- Per-provider token-bucket rate limiter. Alpha Vantage's 25/day budget is spent by a nightly
  batch job only — never by a user-facing request.
- Every response is cached with a TTL keyed to the provider's actual freshness.
- On provider failure, fall through silently but **record the degradation** in a `data_health`
  table and surface it in the UI. Stale data shown as fresh is the failure mode that loses trust.
- Persist every fetch. Never re-request a daily bar you already hold.

### Corporate action validation

Do not apply actions blindly. A bad split ratio from a scraped source silently destroys cost
basis across all history.

Gate: when a detected action would change a position's value by more than 15%, mark it
`applied = false` and require confirmation in the UI. Cross-check the ratio against the price
gap between the prior close and the ex-date open — a genuine 4:1 split shows a ~75% price drop.
If the implied ratio and reported ratio disagree, flag rather than apply.

## 7. Analytics specification

All return series are daily, computed in GBP unless stated. Risk-free rate for GBP Sharpe comes
from FRED SONIA or the UK 3-month gilt — **not** US T-bills.

### 7.1 Position engine

- Maintain both **average cost** (display, matches broker statements) and **FIFO lots** (needed
  for realised gain sequencing).
- UK note: outside an ISA, HMRC requires **Section 104 pooling** with the same-day and 30-day
  bed-and-breakfast rules. Implement pooling for GIA accounts. Inside an ISA there is no CGT, so
  average cost is sufficient — but keep the engine consistent and compute both regardless.
- Apply splits to all historical lots. Apply dividends to `cash_flows`.
- A position is closed when quantity reaches zero; retain it in history with its full realised
  P&L and holding period. Closed positions must remain queryable — "what did I make on things I
  no longer hold" is a first-class view.

### 7.2 Returns

Two figures, always shown together and always labelled:

- **TWR (time-weighted)** — chain daily returns, neutralising the timing and size of deposits.
  This is the only correct basis for comparing against the S&P 500.
- **MWR (money-weighted, XIRR)** — the return actually earned on capital, which reflects
  contribution timing. With regular auto-invest, this diverges materially from TWR. Solve via
  Newton-Raphson on the cash flow series, with bisection fallback for non-convergence.

Presenting only one of these is the most common analytical error in retail portfolio tools.

Daily TWR with flows:

```
r_t = (MV_t - MV_{t-1} - F_t) / (MV_{t-1} + F_t × w)
```

where `F_t` is net external flow and `w` is the day-weight (use 0.5 for mid-day flows, or 0 if
you assume end-of-day settlement — pick one, document it, stay consistent).

### 7.3 Attribution

Contribution of holding *i* on day *t*: `w_{i,t-1} × r_{i,t}`. Contributions sum to portfolio
return. Aggregate across time by chain-linking, not by summing — summing daily contributions over
a year is wrong and will not reconcile to total return.

Produce attribution grids by:

- **Theme** (via `instrument_themes`, honouring partial weights)
- **Sector** (GICS)
- **Geography** — two versions: listing country, and revenue-weighted true exposure
- **Currency** — isolating the FX contribution per §3.2
- **Month / quarter / year** — a calendar heatmap
- **Individual position** — top and bottom contributors for any period

Every grid must reconcile to total portfolio return to within 1bp. Write a test asserting this.

### 7.4 Risk metrics

Rolling 30/90/252-day windows, plus since-inception:

| Metric | Definition | Notes |
|---|---|---|
| Volatility | ann. stdev of daily returns × √252 | |
| Sharpe | (r_p − r_f) / σ_p, annualised | GBP risk-free |
| Sortino | excess return / downside deviation | MAR = 0 |
| Max drawdown | peak-to-trough, with dates and recovery duration | |
| Calmar | ann. return / max DD | |
| Beta | OLS slope of portfolio excess vs benchmark excess | vs both SPX variants |
| Alpha | Jensen's alpha, annualised | report with standard error |
| Tracking error | ann. stdev of active returns | |
| Information ratio | active return / tracking error | |
| Up/down capture | mean portfolio return in up vs down benchmark months | |

**Report standard errors and R² alongside alpha and beta.** With 200 daily observations and a
concentrated portfolio, an alpha estimate typically has an enormous confidence interval. Showing a
bare "alpha: 4.2%" implies a precision that does not exist. Display it as an estimate with a range.

### 7.5 Value at Risk

Compute all three at 95% and 99%, 1-day and 10-day horizons:

1. **Historical** — empirical percentile of the actual daily return distribution. Minimum 252
   observations. This is the primary figure.
2. **Parametric** — variance-covariance. Include for comparison; it understates tail risk.
3. **Cornish-Fisher** — parametric adjusted for skew and kurtosis. The best compromise.

Also compute **CVaR / Expected Shortfall** (mean loss beyond VaR). This is more informative than
VaR and should be given equal prominence.

Constraint to enforce: a portfolio with under one year of history has no meaningful VaR. If the
lookback is insufficient, show "insufficient history" rather than a number computed from 60 days.

Marginal and component VaR per holding — which position contributes most to portfolio tail risk —
is the genuinely actionable output here. Prioritise it.

### 7.6 Factor exposures

Regress portfolio daily excess returns on Fama-French 5 factors + momentum, using the Ken French
Data Library CSVs (free, no key).

Report loadings with t-statistics, R², and rolling 126-day loading charts so factor drift is
visible.

**Caveat to display in the UI:** French's US factors are USD-denominated and US-market. For a
GBP-based portfolio holding UK stocks, run the regression on the local-currency return series and
use the Developed or Europe factor sets for LSE holdings. Do not silently mix.

### 7.7 Relative Rotation Graph

Implement JdK RS-Ratio and RS-Momentum properly — this is easy to get subtly wrong.

```
RS          = 100 × (price_asset / price_benchmark)
RS-Ratio    = 100 + normalised(RS smoothed over ~10 periods)
RS-Momentum = 100 + normalised(rate of change of RS-Ratio)
```

Normalisation is a rolling z-score scaled so values centre on 100 with typical range ~94–106.
Use weekly bars for the default view — daily RRG is noise.

Render with D3: four quadrants (Leading / Weakening / Lagging / Improving), 8–12 week trailing
tails, hover for the underlying series. Support benchmark switching (SPX, FTSE 100, sector ETFs)
and plot both individual holdings and theme aggregates.

Validate against a known reference chart before trusting it.

### 7.8 Concentration and exposure

- Weight tables by position, sector, geography, theme, currency, asset class
- **HHI** (Herfindahl-Hirschman) with an effective-N reading: `1/HHI` = effective number of
  independent positions. A 20-stock portfolio with effective-N of 6 is not diversified.
- Top-1 / top-5 / top-10 weight
- **Correlation matrix** with hierarchical clustering — this is what actually reveals
  diversification. Ten positions across five sectors that all load on the same factor are one bet.
- Rolling average pairwise correlation over time, which rises in stress

### 7.9 Scenario analysis

Two modes:

**Historical replay** — apply the actual daily return path of a stress window to current holdings
via their betas and factor loadings. Windows: GFC (Sep 2008–Mar 2009), Covid crash (Feb–Mar 2020),
2022 rates repricing, Aug 2024 yen carry unwind, and any custom date range.

**Factor shock** — define a shock vector and propagate:

```
Δ portfolio = Σ_i w_i × [ β_i × Δ_market + Σ_k loading_{i,k} × Δ_k ] + fx_effect
```

Preset shocks: equities −20%, 10Y +100bp, GBP/USD ±10%, oil ±30%, VIX to 40, credit spreads +200bp.
Allow combinations, since correlated shocks are the realistic case.

**Label these as estimates.** Beta-propagated scenario analysis assumes stable linear
relationships, and those relationships break precisely in the scenarios being modelled. Say so in
the UI.

### 7.10 Liquidity stress

Per position: `days_to_liquidate = position_shares / (ADV_20d × participation_rate)` at 10%, 20%
and 30% participation.

Aggregate: days to liquidate 50% / 90% / 100% of the portfolio. Flag positions exceeding 5 days.

This matters more for LSE small caps and investment trusts than for US large caps — expect the UK
sleeve to dominate the illiquid tail. Also surface bid-ask spread as a percentage where available,
and note that displayed ADV from free sources is daily-granularity only.

### 7.11 Greeks

Only relevant once options positions exist (Phase 5).

Take provider Greeks from Alpaca where supplied; compute via Black-Scholes where not (deep ITM
contracts often lack provider Greeks). Store `greeks_source` so the two are distinguishable.

Portfolio-level aggregation:

- Net delta, gamma, theta, vega, rho
- **Beta-weighted delta** against SPX — the only delta figure that is meaningful across
  underlyings
- Delta and gamma profile across a ±20% underlying price range
- Theta decay projection to expiry
- Vega exposure bucketed by expiry

BS inputs: spot from the live quote, risk-free from FRED, dividend yield from fundamentals, IV
back-solved from the mid price via Newton-Raphson with bisection fallback.

## 9. Auth

Simplest correct option: **Vercel Deployment Protection** with SSO — zero code, and no
authentication surface to get wrong.

If a custom login is wanted, use NextAuth with an email magic link restricted to a single
allowlisted address in an env var. Never a hardcoded password check.

- All API routes behind session validation, no exceptions
- Cron routes authenticated with a `CRON_SECRET` bearer token, compared in constant time
- `DATABASE_URL` and all keys server-side only, never `NEXT_PUBLIC_`

## 10. Build phases

correct.

Next.js + Drizzle + Postgres. Full schema migrated. Auth working. One account, three instruments,

## 11. Testing requirements

Non-negotiable, because every displayed number depends on the ledger being right:

- **Golden portfolio fixture** — a hand-computed portfolio with ~30 trades spanning buys, partial
  sells, full closes, a 4:1 split, a reverse split, a dividend, a ticker change, and both
  currencies. Every metric asserted against manually verified values.
- **Property test:** attribution always sums to total return.
- **Property test:** position quantity never goes negative on a valid ledger.
- **Property test:** recompute-from-inception always equals the cached snapshot.
- **Unit test:** GBX conversion, both directions.
- **Unit test:** XIRR convergence on pathological flow sequences.
- **Unit test:** BS Greeks against published reference values.

## 12. UI principles

The owner wants this to feel good to use, not just be correct.

- **One dense overview screen.** Total value, day change, TWR/MWR, Sharpe, max DD, top movers,
  concentration warning, upcoming earnings — visible without scrolling.
- **Progressive depth.** Every number on the overview is clickable and opens its full derivation.
  A user should be able to reach the individual trades behind any figure.
- **Data freshness is always visible.** Every quote carries its delay badge. Every analytics panel
  carries its computation timestamp.
- **Uncertainty is shown, not hidden.** Alpha with a confidence interval. Scenario results labelled
  as estimates. VaR suppressed when history is insufficient.
- **Restraint in colour.** Green/red for direction only. Neutral palette everywhere else, so the
  colour that appears actually means something.
- **Fast.** All analytics precomputed. No page should wait on an external API. Quotes stream in
  after first paint and update in place.
